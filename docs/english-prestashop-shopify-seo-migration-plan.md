# English SEO migration plan: PrestaShop and Shopify International

> Working document for planning, implementation, release, and post-release tracking.

| Field | Value |
| --- | --- |
| Status | Draft - pending business and SEO approvals |
| Last updated | 2026-07-17 |
| Shopify store | `https://shop.northfinder.com/` (International / EUR market) |
| English owner | `https://northfinder.com/en/` (legacy PrestaShop) |
| Shopify base branch | `store/international` |
| Primary objective | Keep English on PrestaShop, remove SEO duplication, and avoid disruption to the current International store |

## 1. Executive decision

The migration should be executed in two distinct stages:

1. **Soft consolidation:** keep Shopify English pages available, but point English users and SEO signals to the equivalent PrestaShop English pages. This is the lowest-risk first release because it does not change the International market's default language or URL structure.
2. **Hard removal:** only after a separate root-URL architecture and redirect plan has been approved, change the Shopify default language and remove English from the Shopify market.

Phase 1 reduces search duplication but does **not** physically remove Shopify English pages. Complete removal requires the later cutover phases because English currently owns Shopify's unprefixed root URLs.

## 2. Goals, constraints, and non-goals

### Goals

- Make PrestaShop `northfinder.com/en/` the only preferred English version in search.
- Keep the Shopify International EUR storefront operational for its retained languages and commerce flows.
- Send customers who choose English directly to PrestaShop.
- Consolidate SEO signals page-to-page, not only homepage-to-homepage.
- Preserve the ability to roll back each release independently.
- Define measurable exit criteria for every phase.

### Constraints

- English is currently the Shopify International market's default language, so its URLs have no `/en/` prefix.
- Shopify URL redirects only run for broken/`404` source URLs; they cannot override an active page returning `200`.
- Shopify automatically generates `hreflang` through `content_for_header` while automatic hreflang is enabled.
- PrestaShop and Shopify can use different paths and handles for equivalent products, collections, and content pages.
- `layout/theme.pagefly.liquid` is generated by PageFly and can be overwritten when a PageFly page is republished.
- Changes span multiple ownership boundaries: Shopify theme, Shopify Admin/Markets, PrestaShop, SEO, and possibly edge/DNS infrastructure.

### Non-goals for Phase 1

- Do not change the Shopify store default language.
- Do not remove or unpublish English in Shopify.
- Do not change the `shop.northfinder.com` domain.
- Do not add blanket `301` redirects for active Shopify pages.
- Do not canonicalize unmatched pages to the PrestaShop homepage.
- Do not combine `noindex` with cross-domain canonical consolidation.
- Do not add custom hreflang while Shopify automatic hreflang is still active.

## 3. Current baseline

Verified on 2026-07-17:

| URL / signal | Current result |
| --- | --- |
| `https://shop.northfinder.com/` | `200`; English content; self-canonical |
| `https://shop.northfinder.com/de/` | `200`; self-canonical |
| `https://shop.northfinder.com/hr/` | `200`; self-canonical |
| `https://shop.northfinder.com/sl/` | `200`; self-canonical |
| `https://shop.northfinder.com/en/` | `404`; canonical points to Shopify `/404` |
| Shopify `hreflang="en"` | Points to `https://shop.northfinder.com/` |
| Shopify `hreflang="x-default"` | Points to `https://shop.northfinder.com/` |
| PrestaShop `/` and `/en/` from the current Codex IP | `403` because this IP is blocked by `northfinder.com`; the customer confirms that PrestaShop is operating normally |

Relevant theme implementation:

- `snippets/language-localization.liquid` defines the shared language registry and currently points English to `https://shop.northfinder.com/`.
- `snippets/language-localization-option.liquid` treats every published Shopify language as native. Therefore, changing only the English `fallback_url` will not work while English remains published; the option needs an explicit external override.
- `layout/theme.liquid` and `layout/theme.pagefly.liquid` currently output a self-referencing `canonical_url`.
- Shopify emits its automatic hreflang set through `content_for_header`.

## 4. Target states

### Target after Phase 1: soft consolidation

- English selector links to the corresponding PrestaShop English destination.
- Mapped Shopify English pages remain `200` but have a single canonical pointing to the exact PrestaShop equivalent.
- Unmatched Shopify English pages remain self-canonical until a valid destination is approved.
- PrestaShop English pages are indexable and self-canonical.
- Cross-domain hreflang is reciprocal and contains canonical URLs only.
- Shopify DE, HR, and SL pages remain available and self-canonical.
- Cart, checkout, currency, and retained-market behavior are unchanged.

### Final target after hard cutover

- English is no longer published for the Shopify International market.
- PrestaShop is the only indexable and customer-facing English owner.
- Every retired Shopify English URL either permanently redirects to an equivalent PrestaShop URL or follows an explicitly approved fallback rule.
- Retained Shopify locale URLs have stable, self-canonical URL ownership.
- Shopify and PrestaShop sitemaps contain only their intended canonical URLs.
- Search Console no longer reports Shopify English as the selected canonical.

## 5. Ownership model

| Workstream | Accountable owner | Responsibilities |
| --- | --- | --- |
| Business / e-commerce | Customer stakeholder | Approve English ownership, default language, fallback behavior, and release window |
| SEO | SEO owner / agency | Approve URL mappings, canonical and hreflang clusters, Search Console validation, and monitoring thresholds |
| Shopify theme | Theme developer | Selector behavior, canonical rendering, custom hreflang rendering, PageFly coverage, and theme QA |
| Shopify Admin / Markets | Store admin | Language/default settings, automatic hreflang toggle, translation exports, and redirects eligible for Shopify Admin |
| PrestaShop | Legacy-store developer | Self-canonical, reciprocal hreflang, sitemap, internal links, crawlability, and destination availability |
| Infrastructure | DevOps / DNS / edge owner | Handle active root URLs or cross-domain redirects that Shopify cannot perform |
| Analytics | Analytics / marketing | Preserve attribution and monitor traffic, conversion, revenue, and channel impact |

No phase may be marked complete if a task assigned to another platform is only implemented in the Shopify theme.

- [ ] Inventory PrestaShop English URLs by the same semantic type.

- [ ] Define how collections map to PrestaShop categories.
- [ ] Manually approve CMS, policy, blog, and article mappings.

## 9. Phase 1 - Soft consolidation to PrestaShop English

### Objective

Make PrestaShop the preferred English destination without changing Shopify's default language, published-language state, or commerce routing.

### P1-01 - Produce and validate the canonical URL map

- [ ] Create the master mapping dataset using the schema in Section 14.
- [ ] Generate product candidates from stable identifiers.
- [ ] Generate collection candidates from the approved taxonomy crosswalk.
- [ ] Manually review high-traffic and revenue-critical mappings.
- [ ] Verify every PrestaShop destination returns `200`, is indexable, and does not redirect through multiple hops.
- [ ] Verify mapped source and destination pages are equivalent enough to justify canonical consolidation.
- [ ] Assign every source one of: `mapped`, `self-canonical`, `excluded`, or `blocked`.
- [ ] Obtain SEO approval for the final map.

**Gate:** no canonical code is deployed until the reviewed mapping dataset exists.

### P1-02 - Route the English language selector externally

- [ ] Add an explicit external override to `snippets/language-localization-option.liquid` so a language can use its external destination even when it exists in `localization.available_languages`.
- [ ] Configure the English entry in `snippets/language-localization.liquid` to use the approved PrestaShop English URL and the external override.
- [ ] Preserve Shopify native localization submission for DE, HR, SL, and every other language that remains native to its current market.
- [ ] Verify all selector surfaces: announcement bar, desktop header if present, mobile drawer, and footer.
- [ ] Verify current-language labels, keyboard interaction, focus behavior, and analytics events.
- [ ] Decide whether the selector goes to the PrestaShop homepage or an equivalent current page. Use current-page mapping only if coverage and behavior are reliable.

**Acceptance criteria**

- Choosing English never submits the Shopify localization form.
- The user navigates directly to an approved `northfinder.com/en/` URL.
- Other language choices behave exactly as before.

### P1-03 - Implement conditional cross-domain canonical

- [ ] Define a maintainable mapping delivery method. Recommended: approved mapping data stored against the relevant Shopify resource, with a fixed homepage rule. Do not embed a large, manually maintained URL list in Liquid.
- [ ] Create one shared canonical-rendering implementation used by normal and PageFly layouts.
- [ ] Replace the unconditional self-canonical only for Shopify English pages with an approved mapping.
- [ ] Leave non-English and unmatched English pages self-canonical.
- [ ] Render exactly one canonical tag per page.
- [ ] Use an absolute HTTPS URL.
- [ ] Do not modify canonical client-side with JavaScript.
- [ ] Define a PageFly republish safeguard because `layout/theme.pagefly.liquid` is generated.
- [ ] Add automated checks for duplicate, missing, empty, malformed, or redirected canonical targets.

**Canonical decision table**

| Page context | Canonical behavior |
| --- | --- |
| Shopify EN with approved equivalent | Exact PrestaShop EN URL |
| Shopify EN without approved equivalent | Shopify self-canonical |
| Shopify DE / HR / SL | Shopify self-canonical |
| Cart, account, search, preview, or other excluded route | Preserve platform/default behavior |
| PrestaShop EN canonical page | PrestaShop self-canonical |

### P1-04 - Coordinate cross-domain hreflang

This is a coordinated release across both platforms.

- [ ] Generate page-level alternate sets from canonical URLs only.
- [ ] Make the PrestaShop English URL the `hreflang="en"` member.
- [ ] Keep retained Shopify locale URLs as their corresponding DE, HR, and SL members.
- [ ] Decide and document the correct `x-default` URL.
- [ ] Implement the same complete set on Shopify and PrestaShop pages.
- [ ] Ensure every page references itself and all approved alternates.
- [ ] Ensure pairs are reciprocal across domains.
- [ ] Confirm all alternate targets return `200`, are indexable, and self-canonical.
- [ ] Turn off Shopify automatic hreflang in **Online Store > Preferences** only when the custom cross-domain output is ready on both platforms.
- [ ] Verify no app or theme snippet emits an additional hreflang set.

**Do not:** leave automatic Shopify hreflang enabled and add custom tags on top. Duplicate or conflicting sets can be ignored and can harm search interpretation.

### P1-05 - Fix PrestaShop SEO signals

- [ ] Add or verify self-referencing canonical on all mapped English destinations.
- [ ] Add reciprocal hreflang generated from the same approved mapping source.
- [ ] Confirm no `noindex`, robots block, login wall, bot challenge, or redirect blocks mapped pages.
- [ ] Confirm canonical URLs are included in the PrestaShop sitemap.
- [ ] Remove noncanonical duplicates from the PrestaShop sitemap where applicable.
- [ ] Verify product availability and structured data do not contradict the mapped Shopify source.
- [ ] Confirm Googlebot receives equivalent content and status to a normal browser.

### P1-06 - Update internal and campaign links

- [ ] Replace customer-facing English links in Shopify navigation, banners, footer, content blocks, and apps with direct PrestaShop destinations where appropriate.
- [ ] Review translated menu overrides in Translate & Adapt.
- [ ] Update email, CRM, paid media, affiliate, social, and feed links that intentionally target English.
- [ ] Preserve locale-aware Shopify routes for retained languages.
- [ ] Check that no direct internal link still promotes a noncanonical Shopify English URL when an approved PrestaShop equivalent exists.

### P1-07 - Analytics and attribution readiness

- [ ] Confirm cross-domain tracking between `shop.northfinder.com` and `northfinder.com`.
- [ ] Add both domains to unwanted-referral/cross-domain configuration as required by the analytics platform.
- [ ] Preserve UTM parameters on selector and campaign transitions when approved.
- [ ] Confirm consent state and attribution behavior across both platforms.
- [ ] Create a dashboard segmented by hostname, language, landing page, channel, revenue, and conversion.

### P1-08 - Release and QA

- [ ] Deploy Shopify theme changes and PrestaShop SEO changes in one coordinated window.
- [ ] Toggle Shopify automatic hreflang only after custom tags are available on both sides.
- [ ] Crawl the full mapped URL set.
- [ ] Run the QA matrix in Section 15.
- [ ] Inspect representative URLs in both Search Console properties.
- [ ] Record before/after HTML evidence for canonical and hreflang.
- [ ] Monitor logs and business metrics during the first 24 hours.

### Phase 1 acceptance criteria

- [ ] One canonical exists on every tested page.
- [ ] Every mapped Shopify EN canonical points to the exact approved PrestaShop EN equivalent.
- [ ] Every PrestaShop EN destination is `200`, indexable, and self-canonical.
- [ ] Hreflang sets are singular, canonical-only, self-referencing, and reciprocal.
- [ ] The English selector routes externally on every UI surface.
- [ ] DE, HR, and SL navigation, pricing, cart, checkout, and currency behavior remain unchanged.
- [ ] No significant regression is present in conversion, revenue, error rate, or page performance.

### Phase 1 rollback

1. Re-enable Shopify automatic hreflang.
2. Remove or disable the custom cross-domain hreflang output on both platforms.
3. Restore Shopify self-canonical rendering.
4. Revert the English selector only if the external destination itself is broken.
5. Re-run the critical QA URLs and record the rollback reason.

No language is unpublished in Phase 1, so rollback does not require restoring Shopify translations or locale URLs.

## 10. Phase 2 - Prepare hard removal

### Objective

Prove the future URL architecture and redirect behavior without yet removing English from the live Shopify market.

### P2-01 - Select the final Shopify URL architecture

- [ ] Choose the future default language for the International / EUR market.
- [ ] Determine whether the store-level default language must change or only the market-level default language.
- [ ] Determine the future purpose of `https://shop.northfinder.com/`.
- [ ] Confirm the resulting URLs for every retained language after the default changes.
- [ ] Confirm whether existing `/de/`, `/hr/`, and `/sl/` URLs remain stable, redirect, or become invalid.
- [ ] Confirm the intended `x-default` destination.
- [ ] Obtain business, SEO, and platform-owner sign-off.

### P2-02 - Protect translations and content

- [ ] Export all Shopify translations before any default-language change.
- [ ] Archive theme settings, Markets configuration, navigation, redirects, and relevant app settings.
- [ ] Verify the chosen future default language has complete source content, theme strings, checkout strings, SEO metadata, and app translations.
- [ ] Document restoration steps for translations and default-language settings.

Changing the **store** default language can delete existing translations for the language that becomes the new default. This requires an export and explicit approval. A market-default change and a store-default change must not be treated as the same operation.

### P2-03 - Build the hard redirect matrix

- [ ] Extend the Phase 1 mapping dataset with final redirect status and redirect owner.
- [ ] Mark which source URLs will become `404` and are eligible for Shopify redirects.
- [ ] Mark which source URLs remain active `200` and therefore require another solution.
- [ ] Define exact `301` targets for products, collections, pages, blogs, articles, and the homepage.
- [ ] Define an approved fallback for genuine no-match URLs.
- [ ] Exclude fixed/reserved Shopify paths and transactional URLs.
- [ ] Test for loops, chains, query-parameter loss, case differences, trailing slash behavior, and locale subfolder behavior.
- [ ] Prepare importable Shopify redirect CSV only for eligible broken URLs.
- [ ] Prepare edge/server rules for active URLs only if infrastructure ownership and platform compatibility are confirmed.

### P2-04 - Create a realistic dry-run environment

- [ ] Reproduce Markets, domains, and languages in a test store or controlled test market/domain.
- [ ] Apply the proposed future default language.
- [ ] Remove English in the test configuration.
- [ ] Record actual status/final URL/canonical/hreflang for root, products, collections, CMS pages, and retained language URLs.
- [ ] Import redirect candidates and verify which ones Shopify accepts and executes.
- [ ] Test the edge/server solution for active root URLs if one is required.
- [ ] Test PageFly pages and app-generated routes.
- [ ] Test cart, checkout, account, payments, analytics, feeds, and integrations.

### P2-05 - Write the cutover and rollback runbooks

- [ ] List every change in exact execution order with owner and timestamp field.
- [ ] Define a content/configuration freeze window.
- [ ] Define go/no-go checkpoints.
- [ ] Define critical smoke URLs.
- [ ] Define rollback triggers and who can invoke rollback.
- [ ] Define rollback behavior for default language, Markets assignment, translations, redirects, automatic/custom hreflang, and theme release.
- [ ] Lower DNS TTL in advance only if an approved DNS/edge change is part of the cutover.

### Phase 2 exit gate

- [ ] Final URL architecture is approved.
- [ ] Translation backup and restore are proven.
- [ ] Every retired URL has a tested destination and owner.
- [ ] Every retained locale URL has a tested final behavior.
- [ ] The dry run has no unresolved critical issue.
- [ ] Cutover and rollback runbooks are signed off.

## 11. Phase 3 - Hard cutover

### Objective

Remove English from Shopify and activate permanent URL ownership without breaking retained storefront languages or commerce.

### Pre-cutover checklist

- [ ] Confirm all Phase 2 exit criteria are still valid.
- [ ] Confirm no unreviewed content, navigation, theme, app, or market change occurred after the dry run.
- [ ] Re-export current translations and configuration.
- [ ] Confirm PrestaShop health, capacity, crawlability, sitemap, canonical, hreflang, analytics, and checkout boundaries.
- [ ] Confirm redirect files/rules are the signed-off versions.
- [ ] Confirm monitoring dashboards and incident channel are active.
- [ ] Start the configuration freeze.

### Execution sequence

The exact sequence must follow the validated Phase 2 runbook. The expected order is:

1. [ ] Deploy final PrestaShop canonical, hreflang, sitemap, and internal-link configuration.
2. [ ] Deploy or stage the approved redirect layer for sources that will become eligible at cutover.
3. [ ] Deploy final Shopify theme behavior for the post-English state.
4. [ ] Change the approved Shopify market/store default language.
5. [ ] Remove English from the International market or unpublish it, according to the approved Admin plan.
6. [ ] Activate/import redirects after their source URLs are confirmed broken, or activate the approved infrastructure rules for active URLs.
7. [ ] Regenerate and inspect canonical, hreflang, and sitemap outputs.
8. [ ] Run critical technical and commerce smoke tests.
9. [ ] Run analytics and attribution checks.
10. [ ] Declare go, rollback, or continue-with-fix at the agreed checkpoint.

### Cutover smoke tests

- [ ] Shopify root URL has the approved language and status.
- [ ] Old Shopify English homepage behavior matches the redirect/root decision.
- [ ] Sample old EN product, collection, page, and article URLs resolve exactly once to approved targets.
- [ ] No redirect chain or loop exists.
- [ ] `/de/`, `/hr/`, `/sl/`, and their representative deep URLs have approved status and content.
- [ ] Each retained page is self-canonical.
- [ ] PrestaShop English pages are self-canonical and indexable.
- [ ] Hreflang is reciprocal and contains no retired/redirecting URL.
- [ ] Cart, checkout, payment, currency, tax, shipping, login, and account flows pass.
- [ ] Product feeds, ads, CRM, email, affiliates, and analytics use approved URLs.
- [ ] `404` rate and origin/edge error rate remain below the agreed thresholds.

### Rollback triggers

Rollback immediately when any approved critical condition occurs, for example:

- retained-language storefront or checkout is unavailable;
- redirect loop or large-scale wrong destination is detected;
- PrestaShop cannot serve English traffic reliably;
- canonical/hreflang output is missing or contradictory across a material portion of the site;
- revenue or conversion drops beyond the pre-approved threshold and the change is causal;
- analytics loses cross-domain attribution at scale;
- translation loss cannot be repaired during the release window.

### Phase 3 exit gate

- [ ] All critical smoke tests pass.
- [ ] No unresolved severity-1 or severity-2 incident remains.
- [ ] Redirect and crawler logs show expected behavior.
- [ ] Business, SEO, Shopify, PrestaShop, and infrastructure owners sign off.

## 12. Phase 4 - Stabilization and SEO monitoring

### Objective

Confirm that search engines and customers adopt the new URL ownership without a material business regression.

### First 24 hours

- [ ] Monitor `3xx`, `4xx`, and `5xx` rates by hostname and route type.
- [ ] Monitor redirect loops, chains, and unmatched high-traffic URLs.
- [ ] Monitor storefront availability, conversion, revenue, and checkout errors.
- [ ] Inspect analytics cross-domain sessions and attribution.
- [ ] Validate representative URLs in Search Console.

### First 7 days

- [ ] Crawl both sites daily for canonical, hreflang, redirect, robots, and sitemap drift.
- [ ] Review Googlebot access and bot-challenge logs on PrestaShop.
- [ ] Review top Shopify EN landing URLs that still receive traffic.
- [ ] Add mappings/redirects only through the approved change process.
- [ ] Review paid/organic landing pages and product feeds for old URLs.

### Weeks 2-8

- [ ] Track Google-selected canonical for representative and high-value URLs.
- [ ] Track indexed page counts by hostname and language.
- [ ] Track impressions, clicks, average position, organic sessions, revenue, and conversion.
- [ ] Track crawl anomalies, soft `404`s, duplicate without user-selected canonical, and hreflang errors.
- [ ] Keep redirects stable; do not repeatedly change permanent targets.
- [ ] Review progress weekly with SEO and business owners.

### Phase 4 exit gate

- [ ] PrestaShop English is selected as canonical for the approved sample and high-value URL set.
- [ ] Retired Shopify English URLs are no longer materially indexed or promoted.
- [ ] Retained Shopify languages remain indexed under the approved URLs.
- [ ] Organic and commerce metrics remain within approved thresholds for the agreed observation period.
- [ ] No unresolved systemic canonical, hreflang, redirect, or crawl issue remains.

Search migrations do not have a guaranteed completion date. Keep Phase 4 open until evidence supports closure rather than closing it after a fixed number of days.

## 13. Phase 5 - Cleanup and closeout

### Objective

Remove temporary migration mechanisms, preserve permanent ones, and leave an auditable operating model.

### Tasks

- [ ] Classify each Phase 1 canonical/hreflang mechanism as removable, still required, or permanent.
- [ ] Remove temporary Shopify EN canonical logic only after English URLs are retired and no longer need consolidation.
- [ ] Keep permanent cross-store hreflang only if it remains accurate and has a named owner.
- [ ] Remove obsolete selector flags, mappings, preview code, and release toggles.
- [ ] Keep permanent `301` redirects for as long as legacy traffic/backlinks remain relevant; do not remove them merely because monitoring ended.
- [ ] Do not delete Shopify English translations until business approves permanent deletion. Unpublishing and deleting are separate actions.
- [ ] Update operational documentation for future product, collection, content, language, and domain changes.
- [ ] Archive final mapping dataset, Admin exports, crawl reports, Search Console evidence, release timeline, incidents, and decisions.

## 14. URL mapping specification

The mapping dataset is the central control artifact for canonical, hreflang, redirects, internal links, and QA.

### Required columns

| Column | Description |
| --- | --- |
| `source_url` | Absolute Shopify English URL |
| `source_type` | `home`, `product`, `collection`, `page`, `blog`, `article`, `policy`, or approved extension |
| `source_identifier` | Stable Shopify ID, handle, SKU/reference, or content key |
| `target_url` | Absolute PrestaShop English URL; empty only when no approved target exists |
| `target_identifier` | Stable PrestaShop ID/reference when available |
| `match_method` | `sku`, `legacy_id`, `taxonomy`, `manual`, or approved method |
| `equivalence` | `exact`, `close`, `none`, or `review` |
| `phase_1_action` | `cross-domain-canonical`, `self-canonical`, `excluded`, or `blocked` |
| `phase_3_action` | `301`, `retain`, `404`, `edge-rule`, `review`, or approved action |
| `redirect_owner` | `shopify`, `prestashop`, `edge`, or `none` |
| `priority` | Business/SEO priority such as `critical`, `high`, `medium`, `low` |
| `status` | `candidate`, `reviewed`, `approved`, `implemented`, `verified`, or `rejected` |
| `notes` | Decision rationale, mismatch, dependency, or exception |

### Mapping rules

1. Use stable identifiers before slugs or titles.
2. Canonicalize only equivalent or near-equivalent indexable pages approved by SEO.
3. Use one target per source.
4. Avoid targets that redirect, return errors, are blocked, are noncanonical, or are `noindex`.
5. Do not map many unrelated URLs to the homepage.
6. Keep rejected and no-match rows for auditability.
7. Revalidate targets immediately before both Phase 1 and Phase 3 releases.
8. Use the same approved dataset to generate canonical, hreflang, redirect, and QA expectations to prevent drift.

## 15. QA matrix

Minimum representative coverage:

| Area | Required checks |
| --- | --- |
| Homepage | Status, final URL, language, canonical, hreflang, selector, analytics |
| Product | In-stock, out-of-stock, multiple variants, translated handle, high traffic |
| Collection | Standard, filtered/faceted, pagination, translated handle |
| CMS | Standard page, PageFly page, policy page |
| Editorial | Blog index and article |
| Retained locales | DE, HR, and SL root plus product, collection, and CMS deep URL |
| No-match | Shopify EN page intentionally left self-canonical in Phase 1 |
| Redirect | Exact match, fallback, query string, trailing slash, uppercase/lowercase, nonexistent source |
| Commerce | Currency, price, tax, shipping, add to cart, cart, checkout, payment |
| Account | Login, registration, account callback, wishlist/loyalty integration where applicable |
| SEO | One canonical, one hreflang set, self-reference, reciprocity, indexability, sitemap membership |
| Analytics | Cross-domain session, source/medium, campaign parameters, consent, purchase attribution |
| Performance | No material regression in page load or third-party errors |

### Automated assertions

For each URL under test, assert:

- response status and final URL equal the expected values;
- redirect hop count is within the approved limit;
- canonical count is exactly one;
- canonical target is absolute, approved, and reachable;
- hreflang codes are unique;
- all hreflang targets are canonical `200` pages;
- hreflang sets are reciprocal;
- no retired URL is present in hreflang;
- robots directives do not conflict with canonical/indexation intent;
- rendered language and currency match the expected market;
- no critical console or network error is introduced.

## 17. Risk register

| Risk | Impact | Mitigation | Rollback / response |
| --- | --- | --- | --- |
| Wrong page-to-page mapping | Search signals and users land on irrelevant pages | Stable-ID matching plus manual review of high-value URLs | Revert affected mapping to self-canonical or correct target |
| Duplicate automatic and custom hreflang | Conflicting SEO annotations | Coordinated toggle and full crawl immediately after release | Re-enable one trusted source and remove the other |
| PrestaShop blocks Googlebot | Canonical target cannot be crawled/indexed | Search Console inspection and bot/WAF review before release | Pause canonical rollout or remove affected mappings |
| PageFly overwrites SEO layout change | Canonical/hreflang silently regresses | Shared implementation plus post-publish audit/automation | Republish fixed layout and restore tags |
| Changing default language deletes translations | Content loss | Full export, restore test, and explicit Admin runbook | Restore export and revert default setting |
| Shopify root remains active `200` | Shopify redirect does not run | Decide root architecture and test realistic environment | Keep Phase 1 soft consolidation; do not hard cut over |
| Retained locale URL changes | SEO and customer disruption outside English | Inventory, dry run, and redirect each affected retained URL | Revert Markets/default-language change |
| Redirect chains or loops | Crawl waste and customer failure | Generate and test redirect graph before import | Disable bad rule set and restore previous routing |
| Cross-domain analytics breaks | Lost attribution and unreliable business decisions | Configure and test cross-domain tracking before release | Roll back analytics config or release if decision data is unsafe |
| Canonical target is not equivalent | Google ignores canonical or ranks wrong page | Equivalence classification and SEO approval | Self-canonicalize source until a valid target exists |
| Organic volatility during migration | Temporary traffic/revenue impact | Staged rollout, Search Console monitoring, stable redirects | Investigate by URL class; rollback only when technically justified |
